# Decisions

How this repo is set up and why, plus what's been deliberately postponed.
This file, not any agent's memory, is the record. Update it in the same PR
as the change it describes.

## Decided

| Date | Decision | Why |
|---|---|---|
| 2026-10-13 | **Notes and one tested plugin**, for two readers: people judging how I work, and developers who reuse the setup | Notes show the reasoning; an installable, evaluated plugin shows it ships |
| 2026-10-13 | **MIT licence** for notes and templates | Config and short hooks have no patent surface, so Apache-2.0 adds nothing; one licence keeps reuse simple |
| 2026-10-13 | **Title "Agentic Android"** with the thesis line under it; repo name unchanged for now | Matches the GitHub description; the repo name matters most in an install command, so it waits for the plugin |
| 2026-10-13 | **Status on everything**: each note and the README table says what was verified | The thesis is "no done without proof"; the repo has to meet its own bar |
| 2026-10-13 | **Scope: Android only, general agent lessons allowed**; no KMP/iOS, no agents other than Claude Code, no API how-tos | Focus; [android/skills](https://github.com/android/skills) covers API how-tos |
| 2026-10-13 | **Issues yes, pull requests no** | The repo records my own judgement; outside PRs would also be review work before there's content |
| 2026-10-13 | **`main` protected by a ruleset**: PR required, squash only, no force-push, no deletion, no bypass | Turns "never push to main" from an instruction to agents into something GitHub enforces |
| 2026-10-13 | **PR titles `area: outcome`**; fixes name the claim they correct | Nearly every change is docs, so a `docs:` type prefix would carry no information; area + outcome does |
| 2026-10-13 | **Verified / Not verified lines** in every PR body | Every change on `main` states what was proven |
| 2026-10-13 | **Noreply author email, no AI attribution lines** in commits and PRs | Author lines are public and permanent |
| 2026-10-13 | **Docs live in the repo**, not in agent memory | Anyone, human or agent, picks up the full context from the repo alone |
| 2026-10-13 | **Agents may open PRs; only the owner merges** | `main` is protected by the ruleset, so opening a PR can't change it; merging is the human decision point |
| 2026-10-15 | **Workflow v1 is assembled, not adopted.** No end-to-end framework (superpowers, addyosmani) as a whole. Each stage: read the contenders' actual `SKILL.md`, compare, then pick one, adapt one, or write my own. Candidates live in [workflow-candidates.md](workflow-candidates.md) | None of the eight repos is Android-aware (0 mentions of Android/Gradle/Kotlin in superpowers or mattpocock); the Android verification layer is mine either way. And I have to understand every step, which a framework that drives itself works against |
| 2026-10-15 | **Stage 1 (discovery): my own `discover` skill**, six rules, called only by hand. Open questions one at a time, guesses only when stuck, facts looked up rather than asked, buzzwords challenged, stop when the next three answers are predictable, then restate with Out of scope and an explicit yes. The spec issue (stage 2) holds the result | Accuracy over speed: `interview-me` attaches a guess to every question, which is fast but leads the user; `brainstorming` asks better questions but triggers on everything and is tied to superpowers. Kept short on purpose |
| 2026-10-15 | **Stage 2 (spec): mattpocock `to-spec` as is**, with GitHub Issues as the tracker, followed by my own `builder-check` skill (a fresh subagent that can't ask the author), and a `CLAUDE.md` rule that acceptance criteria say what the screen shows. **Revisit after real use** | The spec is for an agent to build without me. `to-spec` is short, runs only when called, installs on its own and doesn't re-interview. The gaps (builder check, screen criteria) are added around it, not by editing it. Prefer an existing tool until it's seen to fail. addyosmani's spec skill repeats commands, structure and style that live in `CLAUDE.md`, so they'd drift |
| 2026-10-15 | **Stage 3 (design): no new tool.** Hard design questions are discussed in plan mode, `/steelman` is used when wanted, and outcomes go in the decision log | Feature design already happens in the spec and builder-check; the global `CLAUDE.md` already makes the agent Socratic and challenging on design; project architecture is in `android/CLAUDE.md`. Another challenge skill would mean two sets of rules for one job. Revisit with `grilling` if hard questions keep coming up |
| 2026-10-15 | **Enterprise process, kept simple: GitHub for everything.** Spec = issue, slices = sub-issues with blocking links, branch `<area>/<issue#>-<slug>`, PR says "Closes #N", ruleset + CI as gates, Verified lines as Definition of Done. Labels: `ready-for-agent`, `ready-for-human`. No board, estimates or sprints for now. `discover` no longer saves an intent file; the spec issue holds it | Copy the processes whose records someone uses (the agent's brief, the reviewer's PR, the traceability between them), not the ones that coordinate a team. One platform; the skills and templates produce the records, so the process costs almost no manual work. mattpocock's skills are built for GitHub by default and `gh` is already logged in. Jira would add a second system |
| 2026-10-15 | **Stage 4 (plan): mattpocock `to-tickets` as is, then plan mode for each slice** | Agents forget between sessions, so each slice needs a self-contained brief that fits one fresh session; small slices keep PRs reviewable. Detailed plans written up front (superpowers `writing-plans`) go stale once slice 1 changes the code; plan mode plans against the current code |
| 2026-10-15 | **Stage 5 (build process): one slice per session, one PR per slice, merged by me**, run by a small `/slice <issue>` command (to be written after stages 6–8) | Matches ticket → branch → PR → review → merge; keeps PRs reviewable and every step understood. Autonomous parallel building ends in one big PR, and parallel agents on Android share one emulator, so screenshots can't be trusted. Kept as a later experiment |
| 2026-10-19 | **Stage 5 (Android knowledge): Google's `android/skills` and `kotlin-lsp`, plus four rcosteira79 skills copied in: `kotlin-coroutines`, `kotlin-flows`, `android-source-search`, `android-gradle-logic` (the last at project setup).** Copied with credit and the upstream commit noted, not installed as a plugin. Library skills (`datastore`, `paging`, `coil-compose`, `android-retrofit`) only when the app uses that library. Skipped: `android-dev`, `compose`, `modularization`, `android-data-layer`, `koin`. Dispatcher convention decided first, as my own: main-safe callee, injected dispatchers, no stored scopes | A skill should bring knowledge (the traps models get wrong), not conventions that compete with `android/CLAUDE.md`. The skipped ones carry house architecture and DI choices; the plugin installs all 21 and `android-dev` routes work to every one. A skill can also quietly settle a decision left open: `kotlin-coroutines` decides dispatchers, so I decided it first and it now agrees with me. Copying costs automatic updates, so note the upstream commit |
| 2026-10-19 | **Stage 6 (test): rcosteira79 `android-testing` copied in, plus a `CLAUDE.md` rule that tests come from the spec's acceptance criteria. Google `testing-setup` at project creation. Stack decided as mine: Google's defaults (JUnit4, Compose testing, Robolectric, Compose Preview Screenshot Testing, fakes first, MockK only when needed) plus Turbine** | Agents that write code first write tests that copy it; test-first and watching it fail is the cheapest proof a test can catch anything. `android-testing` states that in two lines and adds the Android traps (Compose test dispatcher, two schedulers, semantics before `testTag`), and it resolves the cross-references from the coroutines and flows skills. superpowers (330 lines, delete-and-restart) and addyosmani (398, largely generic) are long; mattpocock `tdd` asks the user to confirm test seams on every slice, which the spec issue already does. `testing-setup` would have settled the open testing-stack item, so it was decided first |
